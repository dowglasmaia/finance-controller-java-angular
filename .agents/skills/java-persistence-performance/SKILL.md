# Java Persistence & Database Performance

Use this skill for persistence and database work in `api-finance-controller`. Treat performance, data integrity, concurrency, and operational rollout as connected concerns. Diagnose before changing mappings or queries; distinguish confirmed defects from risks and hypotheses.

## Project context and boundaries

- Read the root `AGENTS.md` (or applicable platform instructions), `.spec/memory/contexto-tecnico.md`, `.spec/memory/produto.md`, and the relevant approved spec before implementation.
- The backend targets Java 25, Spring Boot 4.1.1, PostgreSQL, Spring Data JPA, Hibernate, and Flyway. Verify effective dependency versions and database behavior in the repository before using version-specific APIs; do not infer Hibernate or Flyway versions from Spring Boot alone.
- The codebase uses Clean Architecture and Spring Modulith. Persistence belongs in infrastructure adapters; keep JPA types out of domain and API contracts. Follow the module's existing ports and use-case boundaries.
- Every tenant-owned repository query must constrain by `owner_id` (P-01). Preserve isolation for reads, writes, bulk operations, and association loading. Money remains `BigDecimal`/PostgreSQL decimal.
- Schema, transactional, or externally observable behavior changes require an approved spec. A skill invocation is not approval to change product behavior.
- Integration tests use PostgreSQL with Testcontainers; do not introduce H2.

## Diagnostic and change workflow

1. Define the observed symptom, affected operation, expected behavior, volume/workload, and constraints. Inspect the use case, adapter, mappings, migration history, configuration, and relevant tests.
2. Gather evidence appropriate to the issue: generated SQL and bind values (redacted), statement counts, Hibernate statistics, execution plans, row counts, transaction boundaries, locks, pool metrics, or migration state. State what cannot be observed and label conclusions accordingly.
3. Explain the root cause and compare viable fixes for correctness, data volume, latency, memory, portability, operational risk, and maintenance cost. Measure before optimizing; do not treat fewer SQL statements alone as proof of improvement.
4. Make the smallest approved change that preserves business semantics and tenant isolation. Do not broaden into unrelated refactoring.
5. Verify with focused tests against PostgreSQL when engine behavior matters, plus migration and query/performance evidence appropriate to the change. Never invent a baseline, claim an unrun check passed, or assert optimality without evidence.
6. Report cause, change, evidence, limits, and remaining risk.

## Non-negotiable safeguards

- Understand SQL generated by ORM mappings and repository methods before changing fetch behavior.
- Never change all relationships to `EAGER` or `LAZY` as a blanket fix. Consider result cardinality, row multiplication, pagination, memory, and transaction scope.
- Scope transaction boundaries explicitly. Analyze propagation, isolation, rollback rules, proxy/self-invocation behavior, flush timing, and external effects; `@Transactional` alone is not a consistency argument.
- Choose concurrency controls from the invariant and actual PostgreSQL semantics. Retries must be bounded, limited to retryable failures, and safe for idempotent operations.
- Treat applied versioned Flyway migrations as immutable. Investigate checksum mismatches; do not auto-repair, rewrite migration history, or use Hibernate schema update as a substitute.
- Do not run destructive SQL, apply production migrations, or make production-impacting changes without explicit authorization and safeguards. Prefer read-only investigation first. Explain data-loss and recovery implications before proposing destructive steps.
- Never expose credentials, secret-bearing URLs, or real financial/customer data in logs, examples, or reports.
